# Student-facing parity and Supabase load audit — 2026-10-11

This is a source-code audit. It does not establish the live health of the Supabase project: no production query, load test, schema change, or write was run for it. Existing working-tree changes were preserved.

## How Streamlit protects the student workflows

| Mechanism | Streamlit evidence | Effect and limit |
| --- | --- | --- |
| Reused client | `streamlit/core/database.py` keeps a lazy Supabase client singleton. | Avoids constructing a client on every request. Its HTTP timeout is 120 seconds, so slow queries can still consume resources. |
| Short-lived caches | `streamlit/core/database.py` caches table reads for 45 seconds; `streamlit/helpers/student_recommendations.py` caches one recommendation calculation for 20 seconds and assignment signals for 45 seconds; `streamlit/helpers/practice_engine.py` caches practice reads for 45 seconds. | Repeated Streamlit reruns need fewer database reads. Mutations selectively invalidate registered cache domains. The generic table loader can still read up to 10,000 rows, so caching alone is not a guarantee of low load. |
| Scoped and bounded reads | `streamlit/core/database.py` attaches `user_id` to owner-scoped tables and reads in pages. Student recommendation history in `streamlit/helpers/recommendation_models.py` uses student IDs, a rolling cutoff, ordering, and per-source limits; assignment signals in `streamlit/helpers/student_recommendations.py` are capped at 800. | Bounds recommendation training inputs and avoids accidental all-user history reads. Authorization still depends on deployed database policies and server credentials. |
| Error handling and diagnostics | `streamlit/core/database.py` classifies timeout errors and captures query exceptions through operational diagnostics. | Gives a recoverable page error and a traceable event. It does not prove that every failed query is harmless to database capacity. |

## Expo comparison

| Area | Current Expo behavior | Gap / risk |
| --- | --- | --- |
| Authorization | `expo/src/services/student-data.ts` obtains the signed-in user and filters student-owned tables by that ID. Browser operations use the publishable key and RLS boundary described in `MIGRATION.md`. | Authenticated RLS acceptance remains required; local code cannot verify the deployed policies. |
| Read size | Student workspace queries select explicit columns in most places, use per-query limits, and scope study/assignment screens. Public practice resources are capped at 120 per type in `expo/src/services/public-data.ts`. | The practice workspace still uses a broad `practice_progress` select and several parallel reads. Limits should be checked against real row counts before changing them, to avoid silently losing history. |
| Repeated navigation | `expo/src/services/student-resource-access.ts` shares a 15-second resource promise by user. Student workspace had no equivalent protection. | A rapid double load could duplicate the same multi-query workspace fan-out. This audit adds in-flight coalescing by user and scope without retaining potentially stale completed results. Post-mutation refreshes bypass an older in-flight read. |
| Timeouts | Public resource loads used `Promise.race` with an 8-second timer. | The timer stopped waiting but left the browser request active. This audit passes an `AbortSignal` to each PostgREST request and clears the timer. Browser abort does not prove the database stops work already started on the server. |
| Model feedback | Streamlit logs recommendation impressions and opens in `user_activity_log` and trains from bounded history. Expo trains the same linear fitting method from 180-day practice and assignment history and derives impression/open samples from canonical exposure telemetry, with adaptive blend calibration. Both telemetry reads are student-scoped, ordered, capped at 800 rows each, cached for 20 seconds, and reduced to the latest 800 combined samples. A separate 800-row assignment history read matches Python's update-date ordering without changing the student assignment screen. | The activity-log and canonical telemetry sources still differ. Exact ranking parity and authenticated RLS/latency remain open; the extra bounded read also needs pilot latency measurement. |
| Failure reporting | Expo surfaces many load errors but has less complete student-side operational diagnostics than Streamlit. | Need request correlation, timeout categorization, and bounded monitoring before declaring the student side production-ready. |

## Priority order

1. Verify one authenticated student's existing read/exposure path with bounded requests and check RLS and request latency. Avoid bulk telemetry repair.
2. Finish student recommendation scoring and feedback through a protected boundary, comparing Python and Expo on fixed fixtures before live use.
3. Reduce broad or duplicate reads only after measuring per-screen query count, row count, payload size, and latency. Preserve complete student history and post-mutation freshness.
4. Compare Home, Practice, Assignments, and Smart Plan end-to-end for loading, retry, completion, review, and recommendation state. Test with one bounded pilot account before claiming hosted parity.

## Changes in this slice

- `expo/src/services/public-data.ts`: timed-out public catalog reads now abort the client request and release the timer.
- `expo/src/services/student-data.ts`: simultaneous reads of the same student workspace scope share one pending promise; completed or failed promises are immediately removed so later reads remain fresh. Practice completion, review requests, video progress, and study-plan requests explicitly bypass an older in-flight read after their writes.
- `expo/src/services/student-recommendation-ml.ts`: the existing bounded workspace trains Streamlit's linear recommendation model in memory. Home's existing session query selects the small score, subject, topic, level, and timestamp fields the model needs. This increases that query's payload slightly but adds no query; the activity-log and adaptive blend path remain open.
- Follow-up: Home and Practice share at most two indexed, student-owned telemetry reads when the 20-second feedback cache is cold, capped at 800 recent exposures and 800 recent open events. Their merged training input is capped at the latest 800 samples. This replaces the missing activity-log feedback input with existing canonical events; no additional telemetry write was added. The adaptive blend is calculated from held-out samples. Newly logged exposures carry learned, heuristic, and final scores plus blend metadata so later feedback has the source's scoring context. The first authenticated latency and RLS check remains for the user.
- 2026-10-12: ML training signals now come from the same 180-day practice/assignment history as Streamlit's report profile, rather than Expo's active learning-program signals. Home loads up to 800 recent practice rows; both models use punctuation-separated topic tokens. A separate student-owned assignment read supplies the model's latest 800 rows by update date, avoiding the general workspace's creation-date cap. This adds one read to Home and Practice workspace loads; its payload is limited to the ten fields used for training. Pilot latency still needs measurement.
- 2026-10-12: Home and Practice now share that assignment-history read for 20 seconds per authenticated student. A fresh workspace load after a practice mutation bypasses the cached result. Failed promises are removed so a temporary query error can be retried. The current immutable preview `7x3poj422f` includes this cache; authenticated latency measurement remains open.
- 2026-10-12: The in-memory resource-scoring model retains all bounded practice types, matching Python's scorer. Its separate held-out diagnostic sample set keeps Python's worksheet/exam/video filter. This changes no database operation.
- 2026-10-12: Profile saves now preserve an existing teacher or student capability when the other mode is selected, matching Streamlit's additive `enable_profile_mode`. This prevents a routine profile update from removing access to teaching or study data. A pure fixture covers both directions and admin-role preservation; no live profile was changed.
- 2026-10-12: Practice draft writes are serialized in the browser; duplicate answer snapshots are skipped, and final submission waits for the pending draft. Each accepted autosave still uses one session write and, as in Streamlit, one bounded owner-scoped delete/insert batch for per-question answers. The number of writes therefore grows with actual edited snapshots rather than overlapping network retries. Live database health and latency remain unmeasured.
- 2026-10-12: Completed practice progress uses one aggregate update per exercise type. Counts and XP now follow Streamlit's per-question and correct-answer rules, including word-search questions. The existing scoped unique key still applies; no new table or index was requested. Live write-path acceptance remains necessary.
- No live Supabase operation, write, or migration was performed during this audit. The dedicated model-history read adds one bounded query to Home and Practice workspace loads and requires pilot latency measurement.
